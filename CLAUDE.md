## Commands

```bash
# Development (runs server on :4000 and Vite on :5173 concurrently)
npm run dev

# Individual processes
npm run dev:server   # Express server with tsx watch
npm run dev:web      # Vite dev server (proxies /api to :4000)

# Production build
npm run build        # Compiles server (tsc) + client (vite) into dist-server/ and dist-client/
npm start            # Runs the compiled server

# Type checking (both client and server)
npm run typecheck

# Smoke/integration tests (boots the real server against a temp DATA_DIR)
npm test

# Visual smoke check (requires a prior `npm run build`; uses local Edge headless,
# seeds demo data, writes mobile + desktop screenshots to verify-shots/)
node scripts/visual-check.mjs
```

`tests/smoke.test.ts` runs with Node's built-in test runner via `tsx` and covers auth, CSRF, uploads, sharing, and admin authorization. CI (`.github/workflows/ci.yml`) runs typecheck, build, test, and a production-dependency audit on every push and PR.

## Architecture

This is a single-repo fullstack photo management app with two separate TypeScript compilation units:

**Server** (`src/server/index.ts`) — single-file Express 5 app compiled with `tsconfig.server.json` (NodeNext modules) to `dist-server/`. It uses Node's built-in `node:sqlite` (`DatabaseSync`) — no ORM, no migration framework, just inline SQL with schema creation and `ensureColumn()` for additive migrations. All business logic, auth, and file handling live in this one file.

**Client** (`src/client/main.tsx`) — single-file React 19 SPA compiled by Vite to `dist-client/`. All components, state, and API calls are in this one file. No routing library; view switching is handled by a `View` state enum. The `api<T>()` helper at the bottom wraps `fetch` with JSON error handling.

The UI is mobile-first: `styles.css` defines the phone layout (bottom tab bar, bottom-sheet modals/info panel) as the default and a single `@media (min-width: 900px)` block switches to the desktop layout (sidebar, centered dialogs, docked info panel). The photo viewer and all overlays render through the `Overlay` portal to `document.body` so `position: fixed` always anchors to the viewport — do not render overlays inline, and do not add `transform`/`backdrop-filter` styles to overlay ancestors. The viewer supports swipe left/right (navigate), swipe down (close), pinch/double-tap zoom with pan, and shows a blurred-thumbnail placeholder until the preview loads. Open overlays integrate with the History API via `useBackClose` (hardware back closes viewer → album → modal instead of leaving the app).

**PWA:** `public/` holds `manifest.webmanifest`, `sw.js` (hand-rolled service worker: offline shell, cache-first hashed assets, never caches `/api`), and icons generated by `scripts/make-icons.mjs`. The manifest declares an Android share target (`POST /share-target`) that the service worker turns into an `/api/assets` upload; the server has a redirect fallback for the same path. The SW registers in production builds only — bump the `CACHE` constant in `sw.js` when changing its caching behavior.

**Uploads** report `{ assets, duplicates, errors }`: each file is SHA-256 hashed on ingest, and per-user duplicates are skipped (or restored if trashed) rather than stored twice. Trashed photos are purged permanently after `TRASH_RETENTION_DAYS` by an hourly maintenance job. `POST /api/assets/zip` streams selected originals as a zip for bulk download. The upload caps (`MAX_UPLOAD_FILE_SIZE_MB`, `MAX_UPLOAD_VIDEO_SIZE_MB`) are exposed via `GET /api/config` so the client shows the limit and skips oversized files before sending; the server still enforces them (multer + an image-size check in `ingestAsset`).

In production, the Express server serves `dist-client/` as static files and catches all non-API routes with an `index.html` fallback (SPA pattern). In development, Vite proxies `/api/*` to Express on `:4000`.

**Data layer:**
- SQLite database at `DATA_DIR/photos.sqlite` (default `./data/photos.sqlite`)
- Each **image** asset is stored as exactly two WebP files under `DATA_DIR/uploads/<userId>/<assetId>/`: `preview.webp` (max 2048px on the longer side) and `thumb.webp` (560px). The uploaded original is **discarded after ingest** — the dedupe hash is computed from the uploaded bytes before conversion, so re-uploading the same source file still registers as a duplicate. The `original` download variant and the zip endpoint serve the 2048px WebP with the original filename's extension swapped to `.webp`. (`assets.original_path` is kept equal to `preview_path` for schema compatibility; `migrateOriginalsToWebp()` converts pre-existing assets on startup and deletes their stored originals.)
- `sharp` handles image processing and EXIF auto-rotation on ingest
- `multer` handles multipart uploads, staging files in `DATA_DIR/tmp/` until `ingestAsset()` has converted them

**Video support:** Uploads accept `video/*` in addition to images. `ingestAsset()` branches to `ingestVideo()`, which (synchronously, so the upload returns fast) probes the file with `ffprobe`, extracts a poster frame with `ffmpeg` → the same `preview.webp`/`thumb.webp` poster pair as images (so the existing `<img>` grid/viewer-backdrop work), stages the source as `source.bin` in the asset dir, and inserts a row with `media_type='video'`, `status='processing'`. A background in-process queue (`enqueueTranscode`/`transcodeAsset`, concurrency `VIDEO_CONCURRENCY`) then transcodes two faststart H.264/AAC MP4s — `video_1080.mp4` (≤1080p) and `video_480.mp4` (≤480p) — flips the row to `status='ready'`, and deletes the source (originals are **not** kept). `resumeVideoProcessing()` re-enqueues interrupted jobs on startup (or marks them `failed` if the source is gone). Video variant endpoints (`video`, `video_sd`, and `original`→1080p `.mp4`) reuse `sendAssetFile`, whose `res.sendFile` already serves HTTP Range requests for seeking; shared albums expose `video`/`video_sd` but not `original`. ffmpeg/ffprobe binaries come from the `ffmpeg-static`/`ffprobe-static` npm packages (no system install). New asset columns: `media_type`, `status`, `duration_ms`, `video_path`, `video_sd_path`. The client shows a play-icon + duration overlay on video tiles (a "Processing…" / error badge while transcoding), plays videos in the viewer with a `<video>` element + an HD/SD quality toggle (swipe/zoom gestures are disabled for videos), and polls the library every 5s while any asset is `processing`.

**Auth:** Cookie-based sessions (`sjodin_session`). Passwords hashed with PBKDF2-SHA256 (310,000 iterations). Sessions stored in SQLite. Two roles: `admin` and `user`. The `requireAuth` middleware attaches the user to the request; `requireAdmin` gates admin routes.

**Shared albums:** Albums can have an optional `share_token`; the `/share/:token` routes serve album contents without authentication. File variants served via `/api/share/:token/file/:assetId/:variant` (thumb/preview and, for videos, `video`/`video_sd` — no original for public access). `POST /api/albums/:id/share` mints/keeps a token; `DELETE /api/albums/:id/share` revokes it (sets `share_token = NULL`) and **never touches the album's assets** — the "Stop sharing" button surfaces this. Asset list responses include `inSharedAlbum` (computed via `sharedAlbumAssetIds`/`assetInSharedAlbum`) so the delete confirmation can warn only when the photo actually belongs to a shared album.

## Environment Variables

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `4000` | Server port |
| `DATA_DIR` | `./data` | Root for SQLite DB and uploads |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | — | Upserts an admin on startup if both are set |
| `APP_ORIGIN` | — | Public origin accepted by the CSRF guard (set to the URL the browser hits) |
| `MAX_UPLOAD_FILES` | `500` | Max files per upload request |
| `MAX_UPLOAD_FILE_SIZE_MB` | `120` | Max file size per image upload |
| `MAX_UPLOAD_VIDEO_SIZE_MB` | `2048` | Max file size per video upload |
| `INGEST_CONCURRENCY` | `3` | Parallel sharp workers during upload ingest |
| `VIDEO_CONCURRENCY` | `1` | Parallel ffmpeg transcodes in the background queue |
| `TRASH_RETENTION_DAYS` | `30` | Days before trashed photos are permanently purged (0 disables) |
| `APP_NAME` | `Sjodin Photos` | White-label display name (UI, page title, PWA manifest via `GET /api/config` and the dynamic `/manifest.webmanifest` route) |
| `APP_SHORT_NAME` | `Photos` | PWA home-screen label |
| `ATTRIBUTION_TEXT` / `ATTRIBUTION_URL` | `Photoalbum by Mats Sjödin` / `https://matssjodin.com` | Footer link on shared album pages; empty text hides it |

If no users exist and `ADMIN_EMAIL`/`ADMIN_PASSWORD` are not set, a dev admin `admin@example.com` / `change-me-before-deploy` is created.

## Docker

```bash
docker build -t sjodin-photos .
docker run -p 4000:4000 -v /host/data:/app/data sjodin-photos
```

The `data/` volume holds both the SQLite database and all uploaded files — it must be persisted across container restarts.
